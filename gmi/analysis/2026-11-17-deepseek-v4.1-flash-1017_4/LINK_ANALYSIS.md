## 结论摘要

1. **断开是被同一节点上新建的连接“撞”掉的。数据层面已基本坐实。**
   - 474 个中途断开中，290 个（61%）在**同一节点**上能找到一个撞人的新连接。对照窗口只有 20 个（4%）。
   - 其中 214 个（45%）的断开时刻，恰好是那条新连接开始拨号后 **1.5 个 RTT** 或 **2.5 个 RTT**。对照窗口中只有 1 个对得上。
   - 1.5 个 RTT 正好走完这样一段路程：
     1. 新连接的 SYN 到达 target；
     2. target 把它当成已有连接的报文，回一个 challenge ACK；
     3. 新连接一侧回 RST；
     4. 这个 RST 回到 target，把已有连接重置。
   - 本机实验复现了这一过程（`out/repro/`）。2.5 个 RTT 的原因待查（2.6 节）。
   - target 会这样处理，前提是两条连接在它看来是**同一个四元组**。这正是 `REPORT.md` 2.5 提出的假设：NLB 开启 client IP preservation，同时源端把同一个源 IP:端口同时用于连两个 NLB IP。
   - 还没确认的是配置层面：NLB 的 client IP preservation / cross-zone 设置，以及 GCP 出口怎样分配源端口。这决定了在哪里修（第 5 节）。
2. **链路类的三种现象都由此产生。**
   - **池中的空闲连接被杀，forward-worker 不知道。**
     - 被杀后 10s 内复用：收到 RST，被 stale 重发救回。24h 共 1,779 次，96.5% 最终成功。
     - 超过 10s 再复用：请求进了黑洞，即 A1/B1，共 2,255 个。
     - 复用时连接已失效的概率，从空闲 0–2s 的 0.19% 一路升到 75–90s 的 8.5%。
   - **进行中的连接被杀**（A2/B2/B3/C1/C2/D2/D3，490 个）：Dynamo 先收到 RST，forward-worker 一直等到 120s 或调用方放弃。
   - **撞人的新连接自己也会变慢**：
     - 约 19% 的新连接只多 1 个 RTT：回完 RST 约 10ms 后就重发 SYN，并且连上了。
     - 约 6.4% 的新连接要么多等 1s（SYN 重传），要么 2.5s 后换到另一个 NLB IP 才连上。
     - 合计约四分之一的新连接撞掉了一条已有连接。
3. **只有 `_4` 有这个问题。**
   - stale 重发：`_4` 一天 1,779 次，全部是 RST。其他所有后端合计 136 次，几乎都是 EOF（对端正常关闭空闲连接）。
   - 首包超时：`_4` 的 903 次中，92% 发生在空闲 ≥10s 的复用连接上，而它所有请求中这类连接只占 44%。其他后端的首包超时与空闲时长无关。
   - forward-worker 所在的两个 GCP 区域、14 个节点都受影响。
   - 失效事件在时间上不扎堆，是一条条连接各自发生的，不是批量刷新。
4. **forward-worker 现有的连接管理发现不了黑洞。**
   - TCP keepalive 为 30s 空闲、30s 间隔、9 次探测，最长约 300s 才判定连接失效。
   - 没有设置 `TCP_USER_TIMEOUT`；首包预算是 120s。
   - stale 重发只覆盖“写完请求 1s 内报错，且 `WasIdle`”的情况。它对 RST 很有效，但救不了黑洞。
   - 24h 内这类挂起累计浪费约 **49.5 小时**请求时间。
5. **修复要两边同时做。**
   - 根因在网络侧修。最直接的是关闭 target group 的 client IP preservation。
   - forward-worker 侧加 `TCP_USER_TIMEOUT` 和安全重发、收紧 keepalive、扩大 stale 重发范围。这些措施不依赖根因结论。
   - 按 2.1 的数据，keepalive 收紧到每 5s 探测一次后，被杀的空闲连接会在 10s 的 RST 窗口内被发现，并移出连接池。这样黑洞基本可以避免。

## 1. 链路与 forward-worker 的连接管理

### 1.1 拓扑（由 trace 确认）

```
调用方 → Cloudflare → gateway ──~2ms──→ forward-worker ──公网（出口 NAT）──→ AWS NLB（两个节点 IP）──→ NodePort 32027 ──→ dynamo-frontend
         (GCP k3s: us-west1 / asia-northeast1)                                         NLB-IP-1
                                                                                       NLB-IP-2
```

- **区域**：gateway 和 forward-worker 部署在 GCP 的两个 k3s 集群里。
  - us-west1：约 68% 流量，到 NLB 的 RTT ≈ 213ms。
  - asia-northeast1：约 32% 流量，RTT ≈ 125ms。
  - 区域由 gateway span 的 `cloud.region` 确认。RTT 的双峰分布与区域一一对应，下文用 RTT 区分区域。
- **节点与 pod**：
  - 当天共出现约 48 个 forward-worker pod，分布在 14 个节点上：us-west1 10 个，asia-northeast1 4 个，平均每个节点 3.4 个 pod。
  - 节点按 pod IP 的 /24 网段区分（flannel 给每个节点分配一个 /24）。
  - 两个集群的 pod 网段重叠，所以同一个 pod IP 可能同时出现在两个区域，区分节点时要同时看区域。
- **协议**：HTTP/1.1 明文。
  - Go 只在 TLS + ALPN 时才走 h2，所以 `ForceAttemptHTTP2` 在这里不生效。
  - span 上带有 `gmi.tcp.done.*` 字段，也说明是 HTTP/1.1。
- **NLB IP**：两个 IP 都在 forward-worker 的 RST 报错里出现过，而且各占一半，例如 `read tcp pod-A1:57416->NLB-IP-1:32027: read: connection reset by peer`。

- **黑洞只出现在空闲 ≥10s 时。**
  - 2,255 个 A1/B1 全部是复用连接，最短空闲 10,067ms。
  - 空闲 <10s 的复用约 9.5 万次/天，其中一个黑洞都没有。
  - A1/B1 的请求都没到 Dynamo：有 Dynamo frontend span 的是 0 / 2,255，而成功请求 100% 都有。
- **RST 在 0–10s 内随空闲时长线性上升**（0.19% → 1.33%），之后基本持平在 1.0–1.5%。**黑洞从 10s 开始出现**，并一直上升到 6.7%。
- **用一个简单模型就能解释这张表**：每条空闲连接以大致恒定的速率被杀（每秒约 0.1%–0.2%）。被杀后 10s 内复用，会收到 RST；超过 10s 才复用，就进了黑洞。
  - 空闲 t < 10s：被杀到复用一定不到 10s，所以只有 RST，比例随 t 线性增长。
  - 空闲 t ≥ 10s：最近 10s 内被杀的仍是 RST，约 1–1.5%，与 t 无关；更早被杀的成了黑洞，比例随 t − 10s 增长。
  - 所以 10s 卡的是“被杀之后过了多久”，而不是“空闲了多久”。24h 的 RST 重发中，64%（1,140 / 1,779）发生在空闲 ≥10s 的连接上。
- **直接交接（idle=0）是例外**：失效率 3.27%，远高于空闲 0–2s 的 0.19%，见 2.2 节末尾。
- **排除“上一个请求留下坏连接”**：`last_data_sent − idle` 近似等于上一个请求的响应时长。A1/B1 与基线的分布几乎一样（p50 1.5s vs 1.4s），说明上一个请求本身没有异常。
- **例子**：
  - B1 `151d2da619a8deabbbac2b535e4c1f0c`：us-west1，pod-E2，复用连接，空闲 30.8s。120s 后返回 504，重试 `_1` 成功。
  - B1 `68f5c09831ca24acf2236380be874495`：asia-northeast1，空闲 66.1s。
  - A1 `ba4d932bd3ca4c9548310644285e348e`：空闲 17.3s，调用方 18.3s 后放弃。

### 2.2 stale 重发日志（24h 全量）与 D1

- **日志是什么**：在复用连接上，如果写完请求 1s 内就报错、且没收到任何响应字节，forward-worker 会换一条连接重发，并记一条 `sender: resending the vendor request after a stale pooled connection`（`sender/staleconn.go:126`）。
- **24h `_4` 共 1,779 条，对应 1,625 次 vendor 调用**：
  - **错误全部是 RST**：读响应时 `read: connection reset by peer` 1,675 条，写请求体时 `write: connection reset by peer` 104 条。
  - **分布**：两个 NLB IP 各占一半（908 / 871）。us-west1 1,358 条，asia-northeast1 421 条，按请求量算分别为 0.97% 和 0.63%。
  - **多轮重发**：146 次调用连续撞上 2 条失效连接，8 次撞上 3 条。
  - **结果**：1,568 次调用（96.5%）最终成功；28 次在重发后仍然挂起，成了 A1/B1。
- **不扎堆**：同一个 pod 在 2s 内又出现另一次重发的，只有 11 / 1,779。所以连接是一条条被杀的，不是 NAT 表、conntrack 表或 NLB 节点的批量刷新。
- **例子**：
  - `c3b0900625e21263c8aaa4982e39c304`：空闲 1,988ms 的连接收到 RST（NLB-IP-2），重发后正常到达 Dynamo。
  - `878585fda5fa57a8c852480957f0c544`：空闲 32,866ms，仍然是 RST（NLB-IP-1）。
  - `a4cf2f67e291a02013704252cde63812`：asia-northeast1，第 3 轮撞上的连接空闲 87,180ms，同样是 RST（NLB-IP-2）。
- **D1（124 个，其中 122 个最终重试 `_1` 成功）分三种**：
  - **74 个是 idle=0 的直接交接**：连接刚释放就直接交给了等待中的请求。Go 把这类交接记为 `WasIdle=false`，不满足 stale 重发条件，直接返回 502。例：`8a361fa3bd7eeb6e5088d958914abd9b`，`read tcp pod-A1:57416->NLB-IP-1:32027: read: connection reset by peer`。
  - **46 个空闲时长 >0**，多数在 30s 以上。vendor 调用开始后 1.2–113s 才收到 RST（p10–p90，p50 14s），超过了 1s 窗口，所以没被重发。也就是说，请求先进了黑洞，过了一段时间才收到 RST。
  - **4 个是新建连接**。
  - **直接交接这一种可能另有原因，暂不深究。**
    - 它的失效率（3.27%）远高于空闲 0–2s（0.19%），用 2.1 的模型解释不了。
    - 在 2.6 节里，D1 能找到同一节点上对应连接的比例也很低（5%，对照 0%）。
    - 可能的原因之一是上一个响应结束时，服务端已经关闭了连接（keep-alive 竞争）。
    - D1 每天只有 124 个。

### 2.3 B2/B3：Dynamo 发出响应头后恰好 1 个 RTT 收到 RST

下表的比值 = (Dynamo 看到断开的时间 − Dynamo 发出响应头的时间) / 该连接自己的 RTT。

| 子类 | 样本 | p10 | p25 | p50 | p75 | p90 |
|---|---:|---:|---:|---:|---:|---:|
| B2 | 44 | 0.20 | 0.76 | **0.98** | 1.01 | 1.02 |
| B3 | 18 | 0.93 | 0.97 | **0.99** | 1.01 | 1.03 |
| C1 | 93 | 1.29 | 1.86 | 4.86 | 13.07 | 20.05 |
| C2 | 43 | 2.14 | 2.52 | 3.17 | 4.66 | 13.57 |
| A2 | 221 | 1.01 | 1.29 | 2.03 | 5.05 | 16.86 |
| D2 | 9 | 1.04 | 1.09 | 1.21 | 1.24 | 1.37 |

- **含义**：
  - 服务端发出的第一个响应包，到了客户端一侧另一台主机（2.6 节：同一节点上那条新连接所在的一侧）。这台主机上没有这条连接，于是立即回了 RST。
  - 这个 RST 的序号恰好是服务端期望的值，所以服务端接受了它，连接被重置。
  - 而真正的 forward-worker 一个字节都没收到。B2/B3 的 vendor_send 都以 120s `context deadline exceeded` 结束，也没收到任何 RST。
- **这一现象排除了三种解释**：
  - forward-worker 主动断开：如果是这样，网关会立刻感知，两端时间会像 D2/D3 那样在约 100ms 内一致。
  - 随机丢包：丢包不会产生 RST。
  - 时钟误差：比值用的是 Dynamo 自己的两个时间戳之差，与两端时钟无关。
- **C1/C2/A2**：forward-worker 已经收到了响应头，断开发生在之后的包上，所以分布更分散。现象相同，只是发生得晚一些。
- **例子**：B3 `114252c11ecd8418873ad03b56c4e3c5`，us-west1，RTT 217ms。Dynamo 在 216ms 发出响应头，430ms 看到断开，间隔 214ms ≈ 1 个 RTT。网关在之后 119.6s 才超时。

### 2.4 新建连接的握手异常

- **正常情况**：新连接的请求约 1.5 个 RTT 后到达 Dynamo：握手 1 个 RTT，加上请求单程 0.5 个 RTT。
- **异常有三簇**（多出的时间 = 请求到达 Dynamo 的时间 − 1.5 个 RTT）：
  - **多 1 个 RTT**（第三版新增）：1,380 个中 265 个（19.2%）。
    - 多出的时间随区域 RTT 等比变化：us-west1 中位 222ms（RTT 214ms），asia-northeast1 中位 148ms（RTT 126ms）。所以是到 NLB 多走了一个来回，不是 DNS；也不是丢包，丢包至少要等 1s 才重传。
    - 这正是本机实验（`out/repro/`）中撞人一方的表现：SYN 换来 challenge ACK，回 RST，约 10ms 后重发 SYN 并连上。
    - 2.6 节显示，中途断开常常恰好发生在同节点上这类连接开始拨号后 1.5 个 RTT。第二版把这一簇当作正常连接，并推测与 DNS 有关，这个推测不成立。
  - **多出约 1.0–1.3s**：对应 Linux 的 SYN 首次重传间隔 1s。
  - **多出约 2.2–2.7s**：Go 把 5s 拨号超时平分给两个 IP。第一个 IP 2.5s 内没握手成功，换到第二个 IP 后立即成功。
- **按请求类型统计**（只统计请求最终到达了 Dynamo 的新建连接）：

| 分组 | 新建连接 | 多 1 个 RTT | 多 ~1s | 多 ~2.5s（换 IP） | 多 1s / 2.5s 合计 |
|---|---:|---:|---:|---:|---:|
| **对照窗口（全部尝试，第二版基线）** | 1,380 | 265（19.2%） | 52 | 35 | **6.4%** |
| 其中成功请求 | 1,364 | 260（19.1%） | 52 | 35 | 6.5% |
| E/F（失败原因是请求内容，与链路无关） | 71 | 10（14.1%） | 6 | 0 | 8.5% |
| A3 | 43 | 7（16.3%） | 3 | 2 | 11.6% |
| 中途断开 A2/B2/B3/C1/C2/D2/D3 | 118 | 25（21.2%） | 5 | 7 | 10.2% |

  另有 20 个（1.4%）多 2 个 RTT，1 个多出 >3s。按区域：多 1 个 RTT 为 us-west1 19.8%、asia-northeast1 17.4%；多 1s / 2.5s 为 6.7%、5.4%。

- **第一版基线 0/94 有偏差**：扩大样本后，成功请求的握手异常率同样是 6.5%。“失败请求更容易出现握手异常”这一旁证不再成立，删去。
- **与请求体大小无关**。异常样本中有很小的请求，例如：
  - `b4d7072847ef45bde99fad0d9765af45`：4.5KB，多 1.2s。
  - `035c2593d1689ce0670b17dc5fcf0cd6`：9.9KB，多 1.2s。
  - `a4f855e75e5551d225a1d1c4a23f3cd1`：1.9KB，多 2.7s。
  - `d71764a1e19828883b55afb4f4497826`：40KB，多 2.5s。
- **普通丢包解释不了**：
  - 同期新建连接的数据段重传率：us-west1 0.063%（53 / 83,808），asia-northeast1 0.050%（24 / 47,950）。握手要多等 1s / 2.5s 的比例（约 6%）比它高出约两个数量级。
  - 丢包只会让握手多等至少 1s，不会只多 1 个 RTT。
  - “第一个 IP 不通、第二个 IP 马上通”也不像整条链路在抖动，更像是某个具体的四元组在 target 侧被占用了。2.6 节直接证实了这一点。

### 2.6 碰撞的另一方：同一节点上的新连接（第二版新增，第三版扩充）

- **做法**：
  - **事件**：474 个中途断开，事件时间 t 取 Dynamo 看到断开的时刻；124 个 D1，t 取请求发出的时刻。
  - **拉取窗口**：
    - 事件窗口：每个事件前 8s 到后 2s 的全部 `_4` 尝试；
    - 对照窗口：2 分钟前同样长度的窗口。
  - **在每个窗口里找**：同区域的新建连接，开始拨号的时间在 t 之前 6s 到之后 0.5s，且握手有异常（2.4 节的三簇）。第二版只用了多 1s / 2.5s 的两簇，第三版加入了多 1 个 RTT 的一簇。
  - **同一节点**：pod IP 的 /24 网段相同，且区域相同。
  - **时间锁定**：断开时刻减去新连接开始拨号的时刻，等于断开连接自己 RTT 的 1.3–1.8 倍（记为 1.5 个 RTT）或 2.3–2.8 倍（记为 2.5 个 RTT）。
    - 多 1s / 2.5s 的新连接：与第二版相同，也允许先加上它 1s 重传或 2.5s 换 IP 的偏移。
    - 多 1 个 RTT 的新连接：只算 1.5 个 RTT，也就是本机实验中的路径。这类连接落在 2.5 个 RTT 附近的匹配，事件窗口 10 个、对照窗口 4 个，与背景水平相当，不计入。如果也计入，下表的时间锁定合计为 219 个、对照 3 个，结论不变。

- **与第二版比较**：
  - 第二版只用多 1s / 2.5s 的新连接作候选。中途断开中同一节点 154 个（32%，对照 1%），时间锁定 111 个（23%，对照 0）。
  - 第三版新增的 103 个时间锁定事件，全部来自多 1 个 RTT 的新连接。
  - 两类另一方没有重叠：每个时间锁定的事件只对应其中一类。
- **多 1 个 RTT 的另一方锁定得非常准**：
  - 中途断开的事件窗口里，同一节点上这类新连接共 179 个：107 个落在 1.3–1.8 个 RTT，其中 99 个在 1.4–1.7 个 RTT 之间。
  - 对照窗口里，同一节点上这类连接有 19 个，落在 1.3–1.8 个 RTT 的只有 1 个。
- **多 1s / 2.5s 的另一方**（与第二版相同）：同节点匹配 176 个。
  - 51 个在 1.5 个 RTT 附近，61 个在 2.5 个 RTT 附近；
  - 9 个是在新连接 1s 重传或 2.5s 换 IP 之后，再过 1.5 或 2.5 个 RTT；
  - 其余 55 个对不上。它们可能是 3.1 节第 3 步的情况：触发 RST 的是服务端发出的数据包，而不是 SYN 本身。
- **1.5 个 RTT 的含义**：新连接的 SYN 到达 target（0.5 RTT），challenge ACK 回到新连接一侧（1.0 RTT），那一侧回的 RST 到达 target（1.5 RTT），已有连接被重置。详见 3.1 节。
- **另一方自己慢多少，取决于它重发的 SYN 是否马上被接受**（3.1 节第 2 步）：
  - 回完 RST 约 10ms 后重发的 SYN 被接受，它只多 1 个 RTT。1.5 个 RTT 锁定的另一方以这一类为主：107 个，多 1s / 2.5s 的只有 51 个。
  - 2.5 个 RTT 锁定的另一方几乎都是多 1s / 2.5s 的：61 个，多 1 个 RTT 的 10 个与背景相当。
  - **推测**：第一次 RST 没能重置已有连接，快速重发的 SYN 又换来一个 challenge ACK，第二个 RST 在 2.5 个 RTT 时才生效。新连接的快速重发已经用掉，只能等 1s 重传，或在 2.5s 时换 IP。
  - 第一次 RST 为什么没有生效，目前没有证据（7.3 节）。第二版把 2.5 个 RTT 解释为“拨号前多了 1 个 RTT（DNS）”，这个解释不成立（2.4 节）。
- **另一方约一半不在同一个 pod 上**：同一个 pod 177 个，同节点其他 pod 178 个（第二版只算多 1s / 2.5s 时为 77 / 99）；每个节点平均有 3.4 个 pod。两个 pod 的 IP 不同，它们的连接能撞上，说明出口处把两者映射成了同一个外部 IP:端口。也就是说，碰撞发生在节点或出口 NAT 这一层，而不只是同一个 pod 内的端口复用（3.2 节）。
- **B2/B3 的时间锁定比例最低（23%），但同节点比例同样高（59%）**。这与 2.3 节一致：B2/B3 多数是被服务端发出的第一个响应包触发的，断开时刻跟着响应头走，而不是跟着另一方开始拨号的时间。
- **断开前后新建连接明显更多**：事件窗口中同区域的新建连接共 2,234 个，对照窗口 536 个，是 4.2 倍。新连接越多越容易撞上，与这个机制一致。
- **仍有约 39% 找不到另一方**，可能的原因（推测）：
  - 另一方的请求没到 Dynamo，无法测它的握手；
  - Go 为某个请求拨的连接，最后给了别的请求用，这次握手延迟不会体现在任何请求上；
  - 另一方不是 forward-worker 的 `_4` 请求。
- **D1**：同一节点有候选的比例为 15%，对照 3%，有一定关联。但 D1 的事件时刻是请求发出的时间，不是连接被杀的时间，无法做时间锁定。另见 2.2 节末尾。

### 2.7 已排除的原因

| 原因 | 排除依据 |
|---|---|
| forward-worker 主动断开 | 代码中只有请求的 ctx 被取消（调用方断开或预算到期）时，才会关闭 vendor 连接。B/C 类网关都等满了 120s，与此矛盾 |
| Dynamo 主动关闭空闲连接 | ① Dynamo 1.6.1 使用 `axum::serve`（axum 0.8.4、hyper 1.7.0），没有设置 timer，hyper 的 `header_read_timeout` 不生效，服务端没有空闲超时。② 服务端正常关闭空闲连接，客户端看到的是 EOF（其他后端都是这样），而 `_4` 全部是 RST |
| 批量失效（NAT 或 conntrack 表整体刷新、NLB 节点切换、pod 重启） | 失效事件不扎堆（2.2、2.5） |
| 单节点、单 pod 或单区域故障 | 见 2.5 |
| 其他后端或 GCP 出口整体的问题 | 只有 `_4` 有（2.5） |
| 时钟误差 | D2/D3 两端相差约 100ms（`REPORT.md` 2.2）；2.3 只用 Dynamo 自己的时间戳。2.6 的时间锁定在两个区域都按各自的 RTT 成比例出现，说明两端时钟偏差远小于 1 个 RTT |
| 普通丢包 | 见 2.4 |

## 3. 机制推断

### 3.1 统一解释：同一个四元组在 target 侧被两条连接共用（主假设 H1）

```
forward-worker 节点 ─┐                 ┌─ NLB 节点 A (NLB-IP-1) ───────┐
                    ├─ 出口 NAT IP:p ──┤                               ├─→ 同一个 target：看到的都是 NAT IP:p → node:32027
forward-worker 节点 ─┘   （p 被复用）   └─ NLB 节点 B (NLB-IP-2)───────┘    （client IP preservation，不做 SNAT）
```

- **前提条件**：AWS 文档在 NLB target group 的 client IP preservation 一节中列出了这个限制。
  - 开启 client IP preservation 后，target 看到的源地址就是 GCP 出口的 NAT IP:port。
  - 如果同一个 NAT IP:port 同时被用来连 NLB A 和 NLB B（目的 IP 不同，NAT 和 Linux 都允许复用同一个源端口），而这两条连接又被转到同一个 target，那么在 target 上它们就是同一个四元组。
  - 在客户端一侧，两条连接的四元组只能靠目的 IP 区分。所以另一方一定连的是另一个 NLB IP。
- **按 TCP 标准行为推演**，可以逐条对上第 2 节的现象。第 1、2 步已由 2.6 节的时间锁定直接观测到。
  1. **新连接 Y 的 SYN 到达 target 时，target 上这个四元组已经有连接 X。** target 按 RFC 5961 第 4 节回 challenge ACK，而不是 SYN-ACK。
  2. **这个 challenge ACK 被送到了 Y 所在的主机。** Y 处于 SYN_SENT 状态，收到一个确认号不对的 ACK，按 RFC 793 回一个 RST，序号等于该 ACK 的确认号，也就是服务端为 X 期望的序号。服务端按 RFC 5961 第 3 节，接受序号完全匹配的 RST，于是 X 在服务端被重置。从 Y 发出 SYN 算起正好 1.5 个 RTT（2.6）。X 的客户端则什么都收不到。
     - X 正在传输响应：表现为中途断开，Dynamo 先感知（A2/B2/B3/C1/C2）。
     - X 在连接池里空闲：变成 forward-worker 不知道的失效连接。之后复用时，被杀后 10s 内会收到 RST（触发重发或成为 D1），超过 10s 则遇到黑洞（A1/B1）。→ 对应 2.1、2.2。
     - Y 自己：Linux 回完 RST 后约 10ms 就重发 SYN，本机实验已验证（`out/repro/`）。这时四元组已经空出来，Y 正常连上，只多 1 个 RTT。→ 对应 2.4 中多 1 个 RTT 的 19%。
     - Y 重发的 SYN 没被接受，或者 challenge ACK 被送到了 X 一侧时，Y 只能等 1s 后重传，或在 2.5s 时换到另一个 IP。→ 对应 2.4 中的 6.4%。challenge ACK 送到 X 一侧时，X 把它当作重复 ACK 忽略，不会回 RST，所以 X 不受影响。
  3. **两条流同时存在期间**，服务端发给 X 的包（例如响应头）可能被送到 Y 那一侧。Y 所在的主机回 RST，X 在 1 个 RTT 后被重置。→ 对应 2.3，以及 2.6 中时间对不上的那部分。
- **10s 阈值**：2.1 的模型说明，10s 是从连接被杀那一刻算起的。最可能的原因是 target 节点上的连接跟踪表：conntrack 看到 RST 后，把表项保留 10s（Linux `nf_conntrack_tcp_timeout_close` 默认 10s；IPVS 的 CLOSE、Cilium 的 `bpf-ct-timeout-regular-tcp-fin` 也是 10s）。
  - 10s 内，复用 X 发出的包仍能匹配表项，被转给 pod。pod 已经没有这条连接，回 RST，forward-worker 能收到。
  - 表项过期后，这些不带 SYN 的包不再属于任何有效连接，被静默丢弃，或者被归到了 Y 的新连接上。
  - 这一步还没有直接证据，需要在 target 节点上看 conntrack 事件确认（5.2）。

### 3.2 发生频率是否说得通

- **观测**：约 26% 的新连接带有碰撞的特征，其中多 1 个 RTT 的约 19%，多 1s / 2.5s 的约 6.4%（2.4）。
  - 按每天约 2 万个新连接估算，约 5,200 次/天，与每天至少约 4,600 次被杀（第 5 节第 2 步）吻合。
  - 另一方约一半在同节点的其他 pod 上（2.6）。
- **跨 pod 也会撞**：两个 pod 的 IP 不同，它们的连接要在 target 上变成同一个四元组，只能是在出口处被映射成了同一个外部 IP:端口。所以碰撞发生在节点或出口 NAT 这一层。
- **如果外部端口是随机选的**（例如节点做 SNAT 时保留 pod 随机选的端口，或随机分配端口）：一条新连接撞上的概率 ≈ 该节点连向另一个 NLB IP 的在用连接数 / 可用端口数（约 2.8 万–6.4 万个）。按每个节点最多几百条这样的连接估算，只有千分之几到百分之一左右，解释不了 26%。
- **如果出口 NAT 按目的地址分别分配端口**：同一个外部端口只要求对每个目的地址唯一，可以同时用于两个 NLB IP。每个节点能用的端口越少，撞上的概率越高。
  - 举例：Cloud NAT 默认每台 VM 只有 64 个端口（`minPortsPerVm`）。如果节点上有十几条连到另一个 NLB IP 的连接，一条新连接撞上的概率就有 20–25%，与观测一致。
  - 本机实验里只给 16 个本地端口时，普通客户端也会自然撞上（`out/repro/` 场景 7）。
- 所以 **GCP 出口的 NAT 类型和端口分配方式是验证重点**（5.3）。

### 3.3 备选解释

| 假设 | 能解释的现象 | 不支持的证据 | 可能性 |
|---|---|---|---|
| H2：GCP 出口 NAT 自身串线，把回程包送到了错误的内网主机（例如多个出口实例共用公网 IP、ECMP 重新哈希） | 2.3 的 RST | 解释不了 2.6：新连接的 SYN 在 1.5 个 RTT 后把服务端的已有连接重置，说明服务端确实把这个 SYN 当成了已有连接的报文，也就是四元组在服务端相同。只靠客户端一侧串线做不到这一点。另外，只有 `_4` 有这个问题 | 低 |
| H3：AWS 侧 NodePort / kube-proxy 的 conntrack 冲突（例如 `externalTrafficPolicy=Cluster` 二次 SNAT 时端口冲突） | 与 H1 相似 | 撞上的另一方几乎都来自同一个客户端节点（2.6）；如果是 target 侧的 SNAT 冲突，任意客户端之间都会撞 | 低。不过 target 节点的 conntrack 仍是 10s 阈值最可能的来源 |

## 5. 验证步骤（按成本从低到高）

2.6 节已经从数据上确认了四元组冲突。下面的检查有两个用途：确定冲突发生在哪一层，从而决定修哪里；以及为修复前后的对比准备指标。

1. **查 AWS 配置**（只读，几分钟）：

   ```bash
   aws elbv2 describe-target-group-attributes  --target-group-arn <tg>   # preserve_client_ip.enabled
   aws elbv2 describe-load-balancer-attributes --load-balancer-arn <lb>  # load_balancing.cross_zone.enabled
   aws elbv2 describe-target-health            --target-group-arn <tg>   # 健康 target 数量和所在 AZ
   ```

   如果“client IP preservation 开启”，并且“两个 NLB 节点都能转到同一个 target”（开启了 cross-zone，或只有一个健康 target），就满足 H1 的前提。

2. **在 Dynamo frontend pod 的网络命名空间里看计数器**（直接证据，也可作为修复后的监控指标）：

   ```bash
   nsenter -t <frontend 进程 pid> -n nstat -az TcpExtTCPSYNChallenge TcpExtTCPChallengeACK TcpExtTCPACKSkippedChallenge
   ```

   - `TcpExtTCPSYNChallenge` 统计的是“已建立的连接上又收到 SYN”的次数。按第 2 节，每天被杀的连接至少约 4,600 条：RST 1,779 + 黑洞 2,255 + D1 124 + 中途断开 490。按 2.4 节新连接的碰撞特征估算，约 5,200 次/天。如果这个计数每天增长数千次，就与之吻合。
   - 在 target 节点上看 `conntrack -S` 中的 `insert_failed`、`drop`、`invalid`。
   - 用 `conntrack -E -p tcp --orig-port-dst 32027` 观察表项的变化过程：收到 RST → 进入 CLOSE → 10s 后被销毁。这样可以确认 10s 阈值的来源（3.1）。

3. **查 GCP 出口**：
   - 确认 k3s 节点是否经 Cloud NAT 出网。
   - 用 `gcloud compute routers nats describe …` 查看 `minPortsPerVm`、`enableDynamicPortAllocation`、`enableEndpointIndependentMapping`、`natIps` 和各项 TCP 超时。
   - 打开 NAT 日志，查是否有同一个 NAT IP:port 同时连接两个 NLB IP。

4. **查 AWS VPC Flow Logs**（NLB 的两个 ENI）：如果同一个 `srcaddr:srcport` 同时出现在两个 NLB ENI 上，就是碰撞的直接证据。

5. **做 A/B 试验**（可回退，不用改代码）：
   - 在一个区域，把 `_4` 的 backend_url 主机名换成其中一个 NLB IP（internet-facing NLB 的每个 AZ 的 IP 是固定的），观察 1–2 小时。
   - 如果 RST 重发、A1/B1、中途断开和握手异常都显著下降，H1 就成立。其中 RST 重发每天 1,779 次，新连接中多 1 个 RTT 的约占 19%，这两项量大，最容易看出变化。
   - 代价：这个区域会暂时失去 NLB 的 AZ 冗余。

6. **定向复现**（第三版新增）：
   - 在一台源端口不会被改写的机器上，用 `out/repro/collide.py` 以同一个源端口分别连接两个 NLB IP。
   - 开启 client IP preservation 时，约 1/K 的轮次中已有连接会被撞断（K 为健康 target 数）；修复后应为 0。
   - 用法和注意事项见 `out/repro/README.md` 第 2 节；对生产 NLB 测试前需按团队流程报备。

## 6. 修复建议

### 6.1 根因（网络侧）

| 方案 | 作用 | 代价 |
|---|---|---|
| **关闭 target group 的 `preserve_client_ip.enabled`**（推荐） | NLB 改用各节点自己的私网 IP 作为源地址，两路连接在 target 上不再是同一个四元组 | Dynamo 看不到真实客户端 IP（目前也没有用到）；需要确认 NodePort 的安全组放行 NLB 子网 |
| 关闭 cross-zone（前提是每个 AZ 都有健康 target） | 两个 NLB 节点不会再转到同一个 target | AZ 之间流量可能不均衡 |
| forward-worker 只连一个 NLB IP，或 NLB 只开一个 AZ | 不再跨 NLB 节点建连 | 失去 NLB 的 AZ 冗余 |
| 调整 GCP 出口 NAT 的端口分配（例如增加每台 VM 的端口数，或改变分配方式） | 降低同一端口同时用于两个 NLB IP 的概率 | 只能降低，无法消除 |

### 6.2 forward-worker 防御（ieops-datachain，不依赖根因结论）

1. **`TCP_USER_TIMEOUT` + 安全重发**：解决 A1/B1，收益最大。
   - 改法：在 `tcpconn.DialContext` 的 `Control` 里给 vendor socket 设置 `TCP_USER_TIMEOUT`，例如 5s（约 25 个 RTT）。这样请求字节 5s 内没被 ACK，连接就会报 ETIMEDOUT。
   - 同时修改 `failedOnStaleConn`：对“复用连接 + 没收到任何响应字节 + ETIMEDOUT”的情况，不再受 1s 窗口限制，判为 stale 连接，重发到新连接。
   - 安全性：TCP 层都没 ACK，说明服务端连请求都没收全，不会重复执行。可以在失败时读一次 `tcpi_unacked` 写进日志，用来佐证。
   - 效果：2,255 个挂起 10–120s 的请求，会在约 5s 后自动在 `_4` 上重发，多数不必再切到 `_1`。
2. **收紧 TCP keepalive**：使用 `net.Dialer.KeepAliveConfig{Enable: true, Idle: 5s, Interval: 5s, Count: 3}`（Go 1.23+）。
   - 按 2.1 的数据，连接被杀后有 10s 的窗口会回 RST。每 5s 探测一次，被杀的空闲连接一定会在这个窗口内收到 RST，被 Transport 移出连接池。这样复用时就不会再撞上黑洞。
   - 窗口外才发现的连接，探测 3 次没有回应后也会在约 15s 内判死。
   - 中途断开的流约 5–20s 就会报错，而不是 120s。
   - 代价：每条空闲连接每 5s 发一个小包。
3. **stale 重发覆盖 `idle=0` 的直接交接**：`staleconn.go:57` 的条件 `info.Reused && info.WasIdle` 改为 `info.Reused`。这样 74 个直接交接的 D1 就能被救回。
4. **改进拨号**：自定义拨号函数，对两个 IP 做 happy-eyeballs 式错峰并发（例如 300ms 后并发连第二个），或者缩短单个 IP 的超时，消除 +2.5s 的延迟。
5. **补可观测性**：
   - 在 `forward_worker.vendor_send` span 上增加 `gmi.conn.local_addr`、`gmi.conn.remote_addr`、`gmi.conn.resend_rounds`。
   - 记录拨号耗时，分开 DNS 和 TCP 握手，并记录实际连上的 IP、是否换过 IP。这样握手异常可以直接从 span 上看到，不用像 2.4 那样间接推算。
   - 失败时记录 `tcpi_unacked`、`tcpi_retransmits`、`tcpi_backoff`。
   - 有了本地端口和 NLB IP，就能与 Dynamo 侧的对端 ip:port 日志（`FIX_PLAN.md` P0-2）和 VPC Flow Logs 逐条对账。
   - 另外，forward-worker-prod 的 span 和日志上 `service.environment` 的值是 `dev`，应改为 `prod`。
6. **设置流式空闲超时**：配合 Dynamo 打开 SSE keep-alive（`FIX_PLAN.md` W5），给这个后端设置 `x-adapter-stream-idle-timeout-ms`。中途断开的流就能在几十秒内结束，而不是等 120s。
7. **不建议把 `IdleConnTimeout` 降到 10s 以下作为长期方案。**
   - 按数据，这样确实能消除 A1/B1（黑洞只出现在空闲 ≥10s）。但约 43% 的请求会改为新建连接，每个多 1 个 RTT。而且约四分之一的新建连接会撞掉另一条连接（2.4、3.2），被撞掉的连接同样会变成黑洞或中途断开。
   - 新连接越多，碰撞也越多（2.6：断开前后新建连接是平时的 4 倍）。
   - 只适合在网络侧修好之前短期止血。
